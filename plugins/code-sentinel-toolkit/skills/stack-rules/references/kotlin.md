# Kotlin

Covers Kotlin on the JVM: server frameworks (Ktor, Spring), AWS Lambda handlers, and libraries.
Gradle Kotlin DSL builds.

## Naming
- Classes/objects `PascalCase`; functions and properties `camelCase`; `const val` and
  top-level immutable constants `UPPER_SNAKE_CASE`.
- Booleans take an `is`/`has`/`should`/`can` prefix (`isActive`), including property getters.
- Backing properties use a leading underscore only for the private mutable twin of a public
  read-only one (`_state` / `state`).

## Typing
- `!!` is the escape hatch equivalent of `any`: flag every new `!!` outside tests. Fix with a
  safe call, `requireNotNull(x) { "reason" }`, or an early return.
- No `Any` / `Any?` in public signatures, DTOs or serialized models; use a sealed type or a
  generic with a bound.
- Unchecked `as` casts: prefer `as?` with a handled `null`, or a sealed `when`.
- `lateinit var` used to avoid modelling nullability is a weak invariant; allowed for
  framework/DI injection and test setup only.
- Platform types (`String!`) leaking from Java APIs into public Kotlin signatures: declare the
  nullability explicitly at the boundary.
- Explicit return types on public and `internal` functions (explicit API mode, if enabled in
  the build, is the bar).
- Impossible states: prefer `sealed interface` / `sealed class` over several nullable fields,
  and `@JvmInline value class` over raw `String`/`Long` for IDs, money and emails.
- Truthiness: not applicable (Kotlin has no truthy/falsy coercion), but flag
  `isNullOrEmpty()` / `isNullOrBlank()` where `null` and empty mean different things.

## Error handling
- `runCatching { }` whose `Result` is ignored, or only `.getOrNull()`'d with no logging: a
  swallowed error.
- `catch (e: Exception) {}`, `catch (e: Throwable)` that does not rethrow, and catching
  `CancellationException` without rethrowing it (breaks coroutine cancellation).
- Coroutines: `launch` on a scope with no `CoroutineExceptionHandler` or supervisor strategy
  where failure matters; `GlobalScope` usage; `async` whose `Deferred` is never awaited.
- Serverless handlers that catch an error and still return a success response or status code;
  batch handlers that do not report partial failures back to the event source.
- Logging: exception passed as the throwable argument (`logger.error("msg", e)`), not
  interpolated into the message, so the stack trace is kept.

## Boundaries
- Layering: handler / route / controller parses and validates input, a use case or service
  holds the logic, a repository owns data access. Flag SDK or database clients called straight
  from a handler or route.
- Blocking calls (JDBC, blocking HTTP clients, `Thread.sleep`, `runBlocking`) inside suspend
  functions or request handlers without `withContext(Dispatchers.IO)`.
- N+1: a data-store read inside a loop or `map { }` (`getItem` / `query` / a SELECT per element)
  where a batch read exists; unbounded scans or queries with no pagination.
- Clients (HTTP, SDK, database pools) created per request or per invocation instead of once.

## State and lifecycle
Not applicable for server code. For Android UI code, apply `react-native.md` concepts by
analogy: collect flows lifecycle-aware, cancel scopes on teardown.

## Testing
- Frameworks: JUnit 5, Kotest; mocking with MockK. Tests under `src/test/kotlin`, integration
  tests often in a separate source set (`src/integrationTest`).
- Coverage: read the minimum from Kover (`kover { reports { verify { rule { minBound(...) } } } }`)
  or JaCoCo (`violationRules`) in `build.gradle.kts`. Cite the file and value.
- Coroutine code is tested with `runTest`, not `runBlocking` with real delays.
- Data-access code has at least one test against a real local dependency (container or
  local emulator), not only mocks.

## PR size exclusions
`gradle.lockfile`, `*.lockfile`, `gradle/wrapper/**`, `gradlew`, `gradlew.bat`, generated
sources under `build/`, API dump files (`*.api`) when regenerated by a tool.

## Sensitive paths
Auth/authorizer handlers, token or signature validation, IAM or credential handling,
payment code, schema or data migrations, serialization of personal data.
